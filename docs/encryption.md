# Cryptographic Architecture & Authenticated Encryption

## 1. Cryptographic Principles in StegoVault

Steganography alone provides **security through obscurity**; an adversary who knows or suspects the embedding algorithm can trivially extract the raw bits.

To provide true confidentiality, integrity, and authenticity, StegoVault enforces authenticated symmetric encryption prior to embedding:

$$\text{Plaintext} \xrightarrow{\text{PBKDF2} + \text{AES-256-GCM}} \text{Ciphertext} + \text{Tag} \xrightarrow{\text{Container Packaging}} \text{Payload} \xrightarrow{\text{Spatial LSB}} \text{Stego-Image}$$

Even if a forensic investigator detects the presence of hidden data using statistical steganalysis, they are faced with ciphertext that is indistinguishable from true random noise. Without the secret passphrase, extracting the plaintext is computationally infeasible.

## 2. Key Derivation: PBKDF2-HMAC-SHA256

User-supplied passphrases have varying and often low Shannon entropy. Converting a variable-length passphrase into an evenly distributed 256-bit cryptographic key requires a modern Key Derivation Function (KDF).

StegoVault uses **PBKDF2** (Password-Based Key Derivation Function 2) parameterized as follows:
- **Pseudorandom Function (PRF):** HMAC-SHA256
- **Work Factor (Iterations):** $600{,}000$ rounds (aligned with current OWASP recommendations for password hashing/derivation)
- **Salt Length:** 16 bytes (128 bits), drawn directly from the operating system's Cryptographically Secure Pseudorandom Number Generator (CSPRNG via Python `os.urandom`)
- **Key Length:** 32 bytes (256 bits)

$$K = \text{PBKDF2-HMAC-SHA256}(\text{Password}, \text{Salt}, \text{iterations}=600{,}000, \text{dkLen}=32)$$

### Defeating Precomputation & Rainbow Tables
Because a fresh 16-byte salt is generated for every single encoding operation, no two encryptions will produce the same derived key—even if the user encodes identical messages with the identical password into multiple images.

## 3. Authenticated Encryption: AES-256-GCM

StegoVault utilizes **AES-256-GCM** (Galois/Counter Mode), an AEAD (Authenticated Encryption with Associated Data) scheme specified in NIST SP 800-38D.

### Architecture
1. **Confidentiality:** Encryption uses AES in Counter (CTR) mode with a 256-bit key. Plaintext blocks $P_i$ are XORed with successive keystream blocks generated by encrypting incrementing counter values:
   $$C_i = P_i \oplus \text{AES}_K(\text{IV} \parallel \text{Counter}_i)$$
2. **Authenticity & Integrity:** GCM computes an authentication tag $T$ over the ciphertext using universal hashing in the finite field $\text{GF}(2^{128})$ (GHASH):
   $$T = \text{GHASH}_H(A \parallel C \parallel L) \oplus \text{AES}_K(\text{IV} \parallel 0^{31}1)$$
   Where $H = \text{AES}_K(0^{128})$ is the hash subkey.

### Parameters
- **Key Size:** 256 bits (32 bytes)
- **Nonce / IV:** 96 bits (12 bytes), generated via CSPRNG
- **Authentication Tag:** 128 bits (16 bytes)

### Why Authenticated Encryption is Essential
Unauthenticated modes (such as AES-CBC or raw XOR) are vulnerable to bit-flipping attacks. An adversary intercepting a stego-image could flip LSB bits to alter specific plaintext characters without knowing the key. In AES-GCM, any bit modification in the ciphertext causes authentication verification to fail immediately:

$$\text{Verify}(K, \text{IV}, C, T) = \text{False}$$

## 4. Tamper Detection & Verification Flow

StegoVault employs a 3-layer integrity verification architecture:

```
+-------------------------------------------------------------+
| Layer 1: Container Header Integrity                         |
| Algorithm: CRC32 over the 60-byte header prefix             |
| Defense: Detects file truncation or non-StegoVault images   |
+-------------------------------------------------------------+
                              | Passes
                              v
+-------------------------------------------------------------+
| Layer 2: Total Payload Container Hash                       |
| Algorithm: SHA-256 over entire binary payload               |
| Defense: Verifies complete uncorrupted bit stream extraction|
+-------------------------------------------------------------+
                              | Passes
                              v
+-------------------------------------------------------------+
| Layer 3: Cryptographic Ciphertext Authentication            |
| Algorithm: 128-bit AES-GCM Authentication Tag verification  |
| Defense: Validates key correctness & defeats bit-tampering  |
+-------------------------------------------------------------+
```

## 5. Security Properties & Hardening

1. **Zero Information Leakage on Failure:** If password verification fails or ciphertext is modified, the backend returns a generic `AuthenticationFailedError`. It never exposes partial decrypted bytes or timing variances that could assist an attacker.
2. **Constant-Time Comparisons:** All cryptographic checks, hashes, and authentication tags use `hmac.compare_digest` to prevent side-channel timing attacks.
3. **Log Sanitization:** Passwords, derived keys, plaintexts, and nonces are strictly excluded from all application logs and error traces.
